# GBA record layout in Clang

The patch targets bare-metal AArch32 `-mabi=apcs-gnu`, as used by the ARM7TDMI/Thumb-1 game build. It carries the changes from LLVM commit `37a0a216311` (clang `24.0.0git`). Apply it to LLVM commit `04c4ab8d9a15c548bfd472abd3407bc0be1e137e` from the LLVM checkout:

```sh
git am ../gba-omvll/patches/clang-apcs-struct-boundary.patch
```

## GCC reference behavior

- APCS-GNU defaults to a **32-bit minimum record alignment** for structs and unions, including char-only structs. Rounding to the record alignment determines both `sizeof` and array stride. An explicit larger alignment still applies. A packed record has no minimum from the ABI; `#pragma pack` caps the minimum for unpacked records.
- Unpacked bitfields fit within naturally aligned containers of their declared type. Named bitfields can raise record alignment; unnamed bitfields cannot. A zero-width field still moves placement to its type's alignment boundary, even in a packed record. An explicit bitfield alignment, capped by `#pragma pack`, is applied before checking the natural container fit.
- AAPCS defaults to an **8-bit minimum**, not 64. Explicit 64 is effective for AAPCS; APCS-GNU falls back to its default. `OamData`'s tested bit offsets already matched in APCS-GNU; its record alignment was 2 bytes in old Clang and is 4 bytes in GCC and patched Clang.

## Clang changes

`clang/lib/Basic/Targets/ARM.{h,cpp}` selects the bare-metal APCS rules without changing Darwin APCS or default AAPCS. `clang/lib/AST/RecordLayoutBuilder.cpp` applies the target's minimum alignment and bitfield placement rules; existing CodeGen consumes the corrected AST layout. `Options.td`, the ARM driver in `ToolChains/Clang.cpp`, and `CompilerInvocation.cpp` accept `-mstructure-size-boundary=8|32|64` for AArch32 ELF through both the driver and cc1. The override is included in the module cache key and serialized target options. `clang/test/CodeGen/arm-structure-size-boundary.c` checks layout and IR array types.

## Evidence

The [comparison harness](../scripts/layout-compare.py) reads constants and initialized bitfield positions from ARM ELF objects generated by Wonderful GCC 16.2 and Clang. From the `gba-omvll` checkout:

```sh
python3 scripts/layout-compare.py --explicit
python3 scripts/layout-compare.py --game --game-dir ../fufufu
```

Defaults locate Clang and picolibc in sibling `toolchain/llvm` and GCC in the Wonderful installation. Override these with `--clang`, `--libc-include`, and `--gcc-prefix` as needed. With the patched compiler:

- `--explicit`: **0/120 differences per configuration**, with APCS-GNU and AAPCS defaults and explicit 8/32/64-bit boundaries.
- `--game`: **0/48 differences per tested game configuration**, including default APCS-GNU and default-boundary AAPCS. The game control uses `-fno-short-enums` for AAPCS because GCC's short enums reject some game bitfield declarations. The comparison used headers without either temporary `_Alignas(4)` workaround.

For APCS-GNU, the verified values include `sizeof(SaveBlock1) = 15568`, `sizeof(SaveBlock2) = 3884`, `sizeof(Pokeblock) = 8`, and `offsetof(SaveBlock1, berryBlenderRecords) = 0x9BC`. The tested game TUs, including `save.c` and `sprite.c`, compiled without the workarounds. The change does not address pre-existing AAPCS differences for some explicitly aligned bitfield combinations.

The corrected ABI also makes `CMD_ARGS`'s `s16` struct overlay require
4-byte alignment. The ROM explicitly aligns its backing `gBattleAnimArgs`
array instead of relying on GCC to issue two halfword loads. This is
a source alignment requirement, not a compiler workaround.
